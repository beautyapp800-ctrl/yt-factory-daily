# YouTube Content Factory

Система, яка щодня автоматично робить відео для YouTube-каналу про стоїцизм і
практичну філософію (англійською, 25–35 хв) і публікує їх.

**Поточний стан:** реалізовано `topic`, `script`, `tts` і `images`. Решта етапів — заглушки.

## Налаштування

```
cp .env.example .env
```

Далі впиши в `.env` ключ `GROQ_API_KEY` (https://console.groq.com/keys).
`GEMINI_API_KEY` необовʼязковий: якщо він є, Gemini працює як резерв, якщо ні —
резерв просто пропускається. Файл `.env` у `.gitignore`, комітити його не можна.

Для озвучення (`tts`) потрібен один із двох провайдерів:

- **piper** (за замовчуванням, офлайн): `pip install piper-tts`, потім завантаж
  голоси (~236 МБ, у `.gitignore`, не комітяться):
  ```
  python -m piper.download_voices --download-dir assets/voices en_US-ryan-high en_GB-alan-medium en_US-joe-medium
  ```
- **edge-tts** (хмара Microsoft, безкоштовно, без ключа): `pip install edge-tts`.
  З деяких серверних IP повертає 403 — це видно в лозі як зрозуміле пояснення,
  не стектрейс, і означає "спробуй piper на цій машині".

Обирається полем `tts.provider` у `config.json` (`"piper"` або `"edge"`).
`ffmpeg` має бути в PATH — використовується для конвертації mp3→wav (edge) і для
склеювання сцен в один `narration.wav`.

Для ілюстрацій (`images`) потрібен Cloudflare Workers AI:

- Безкоштовний акаунт на dash.cloudflare.com, картка не потрібна.
- `CLOUDFLARE_ACCOUNT_ID` — зі сторінки Workers AI, панель «Use REST API».
- `CLOUDFLARE_API_TOKEN` — My Profile → API Tokens → Create Custom Token з правами
  `Account` / `Workers AI` / `Read` **і** `Account` / `Workers AI` / `Edit` (обидва
  одночасно), Account Resources звужено до одного акаунта.
- Резерв — `POLLINATIONS_TOKEN`, той самий, що й вище.

Безкоштовний ліміт — 10 000 Neurons/добу, поновлюється щодня.

OCR-перевірка (опційна, можна пропустити — усе працює й без неї):

```
winget install --id UB-Mannheim.TesseractOCR -e
pip install pytesseract Pillow
```

Якщо `tesseract.exe` не знайдено, перевірка просто вимикається, без помилки.

## Запуск

```
python run.py            # створює запис у БД і проходить усі етапи
python run.py --dry-run  # лише показує етапи, БД не чіпає
python tests/test_failure_path.py
```

Потрібен Python 3.11+. Зовнішніх залежностей немає, лише стандартна бібліотека.

## Структура

- `config.json` — налаштування каналу, відео, `image_style`, блок `tts`
- `run.py` — оркестратор (помилка етапу → статус `failed`, процес не падає)
- `core/` — config, db (SQLite), logger, retry, validate, llm, prompts, text, tts
- `pipeline/` — етапи: topic, script, tts, images, render, thumbnail, seo, upload
- `scripts/preview.py` — показує заголовок, засів, уроки й перші речення кожної
  частини одного відео, без читання 5000 слів
- `scripts/tts_sample.py` — рендерить один уривок усіма голосами-кандидатами,
  щоб вибрати голос на слух
- `scripts/contact_sheet.py` — складає всі зображення відео в одну сітку
  (`output/<video_id>/contact_sheet.jpg`), щоб оцінити узгодженість набору
  одним поглядом, не відкриваючи по одній
- `assets/topic_seeds.json` — 48 стоїчних тем-засівів
- `assets/voices/` — моделі Piper (у `.gitignore`, качаються окремо)
- `data/factory.db` — база (у `.gitignore`)
- `output/<video_id>/` — `concept.json`, `outline.json`, `script.txt`,
  `narration.wav`, `audio/scene_NNN.wav`
- `logs/factory.log` — лог (у `.gitignore`)

## Як працює генерація

**`core/llm.py`** — Groq (`llama-3.3-70b-versatile`) основний, Gemini резервний.
Не більше 25 запитів на хвилину, окрема обробка 429 з очікуванням замість падіння,
`complete_json()` вміє витягати JSON із ```json-блоків і перепитує, якщо парсинг
не вдався. Кожен виклик логується: модель, токени, час.

**`pipeline/topic.py`** — бере засів, який найрідше використовувався (рахується
по колонці `videos.seed`), просить у моделі концепцію, перевіряє на дублі через
`topic_exists()` і схожість ≥0.75 з останніми 200 темами. До 5 спроб із різними
засівами.

**`pipeline/script.py`** — чотири стадії, не один запит:

| Стадія | Що робить | Запитів |
|---|---|---|
| A | план: заголовок, обіцянка, 10 назв уроків | 1 |
| B | кожен урок окремо (~395 слів), з передачею вже написаного | 10 |
| C | гачок (~200 слів) і фінал (~200 слів) | 2 |
| D | розбивка на сцени **програмно** + image_prompt пакетами по 10 | ~5 |

Бюджет слів (`pipeline/script.py:word_budget`) рахується з реального часу, а не
як `хвилини × слів/хв`: тривалість = мовлення + паузи, а паузи (між реченнями, сценами
й уроками, `config.tts.pauses`) ростуть разом зі скриптом. Структура скриптів виміряна
на п'яти відео (речення кожні 21.4 слова, сцена кожні 92.3), і рівняння розв'язується
точно. Для 30 хв при 166 слів/хв це **4797 слів**; паузи — 3.7% часу. Стара фіксована
частка 7% завищувала паузи, а після скорочення пауз до 220/450/900 мс застаріла б ще
більше. Перевірено: модель передбачила для відео 7 25.64 хв, фактично вийшло 25.04
(для тексту з іншою структурою, ніж усереднена), а для відео 8 скрипт з 4693 слів
озвучився у **29.99 хв**.

`config.words_per_minute = 166` — це темп, виміряний на двох цілих відео з голосом
Andrew (`-5%`): 169.8 слів/хв на відео 7 і 162.7 на відео 8, разом 8791 слово за
52.9 хв. Розкид між відео ±2.5% — це та сама голосова модель, але різний текст, і саме він
визначає, наскільки точно можна влучити в хвилини. На уривку з 310 слів вийшло 169.5.

Перед записом у БД перевіряється: сума слів у межах ±4% бюджету (28.8–31.2 хв за
номінального темпу; з виміряним розкидом темпу 162.7–169.8 слів/хв приймений скрипт
укладається в 28.3–31.9 хв, тобто в 28–32), 40–60 сцен,
у жодній сцені немає markdown і порожнього тексту, у кожної сцени є image_prompt.
Якщо слів не вистачає або забагато — перегенеровуються лише найгірші уроки
(до 3 раундів), а не весь сценарій. Кількість сцен коригується програмно зміною
цільового розміру сцени.

Кожен урок прив'язаний до теми засіву явно (назва + `angle_hints`), і план
відкидається, якщо більше 4 з 10 уроків потрапляють в один домен (телефон,
робота, сім'я...) — щоб 30 відео не зійшлися в узагальнену самодопомогу. Власні
імена й рідкісні кольори, якими зловживала модель у минулих відео, записуються
в таблицю `tics` і забороняються в наступних промтах; ім'я, повторене в одному
відео більше 3 разів, замінюється програмно.

**`pipeline/tts.py`** — кожна сцена озвучується окремо
(`output/<video_id>/audio/scene_NNN.wav`), потім склеюються в `narration.wav`.
Голос остаточно: **`en-US-AndrewMultilingualNeural`, rate `-5%`**, паузи між реченнями /
сценами / уроками **220 / 450 / 900 мс**. Реальний темп (слів/хв) вимірюється з готового
аудіо і звіряється з `config.words_per_minute`; відхилення понад 15% пишеться в лог і в
`events` як попередження, не як помилка — саме відео при цьому не відкидається.

Варіацію інтонації (свій rate і pitch на кожне речення, питання вище й повільніше,
перше речення уроку повільніше) було зроблено, виміряно і **прибрано за рішенням
власника каналу** — голос лишається рівним. Що показало вимірювання, якщо до цього
колись повернутись: edge-tts слухається rate (+1.2% швидкості на кожен запитаний
пункт, кореляція 0.65 на 70 реченнях) і значно гірше pitch (кореляція 0.34, середній
ефект +1.4% для «вище» і -1.6% для «нижче»); повторний синтез того самого тексту з
тими самими параметрами дає ту саму довжину, але не ті самі байти (шум на боці
Microsoft, до 9% повної шкали); а питань у скриптах 1–10 на відео, тож правило про
питання майже нічого не змінювало.

**`pipeline/images.py`** — кожна сцена отримує кілька зображень:
`max(1, round(duration_s / images_per_seconds))`, усі на одному `image_prompt`,
кожне зі своїм seed. Порядок відкату на зображення: Cloudflare Workers AI
(`flux-1-schnell`) → pollinations.ai → повторне використання останньої вдалої
картинки (без копіювання файлу, просто той самий шлях ще раз) — справжньою
відсутньою залишається лише перша картинка відео, якщо вона не вийшла, бо
дублювати ще нічого. Перші 5 успішних генерацій Cloudflare логують реальний
Neurons (виміряно: **96 на картинку при `steps=2`**, не орієнтовні ~19–20 з
документації провайдера), і стадія рахує прогноз на все відео проти ліміту
10 000/добу з явним попередженням, якщо не влазить.

Перед генерацією кожен `image_prompt` проганяється через список заборонених
слів (`core/prompts.py:IMAGE_BANNED_WORDS`) і переписується моделлю, якщо
знайдено збіг; виправлення пишеться назад у `scenes.image_prompt`. Список
навмисно вузький: у ньому лише слова, які **самі є написом** — етикетка, вивіска,
логотип, заголовок, підпис, гравіювання. Самі предмети (телефон, ноутбук,
коробка, книжка) дозволені. Ширший список теж працював проти псевдотексту, але
виштовхував модель у взаємозамінні пейзажі й порожні дверні прорізи, які не
ілюстрували нічого конкретного — це коштувало більше, ніж сам псевдотекст.
Правильний прийом — показати предмет без напису (руки з немаркованим пакунком;
світло екрана на обличчі, сам екран за кадром), і він розписаний прикладами в
`IMAGE_SYSTEM`. FLUX на `steps=2` майже ігнорує негативні інструкції в стилі
(«no text»), тож прибирати треба на етапі, де LLM пише промпт. Опційний другий шар — OCR через Tesseract по готовій картинці;
**перевірено на реальному прикладі з текстом — не спрацював** (ШІ малює
псевдотекст, що не формує справжніх гліфів, а Tesseract натренований на
реальних шрифтах), тож це радше остання сітка безпеки, ніж основний захист.

## SEO і обкладинка (`pipeline/seo.py`, `pipeline/thumbnail.py`)

Порядок етапів у `run.py`: **seo → thumbnail**. Слова на обкладинці беруться із
заголовка, який побачить глядач, тобто з результату seo, а не з робочої назви скрипта.

**SEO** — один запит до LLM за заголовком, обіцянкою і планом уроків. Що рахується в коді,
а не просять у моделі: таймкоди (з `timings.json`), заклик підписатись (фіксований текст) і
кожне обмеження на відповідь. Відповідь, що їх порушує, повертається моделі з переліком
причин, до 3 спроб, далі етап падає, а не пише напівправильне.

- **title** — до 70 символів, без двокрапки, емодзі й хештегів; якщо в ньому є число, воно
  має бути справжньою кількістю уроків (заголовок «12 уроків» над відео з 10 відхиляється).
  Формат «число + обіцянка»; число не обов'язкове (приклад із завдання «NEVER Explain
  Yourself Again» його не має), відсутність лише логується.
- **description** — гачок (до 150 символів, закінчується крапкою: це все, що видно в
  пошуку), порожній рядок, підсумок із 3–4 речень, порожній рядок, список уроків із
  таймкодами (`0:00 Introduction`, потім кожен урок, потім `Closing thoughts`), порожній
  рядок, заклик підписатись. Формат таймкодів `m:ss`, з години — `h:mm:ss`. Таймкоди
  рахуються від початку `voice.mp3`: якщо перед озвучкою колись поставлять інтро, усі
  вони зсунуться на його довжину.
- **tags** — 12–15, малими літерами, без `#`, до 30 символів кожен, `stoicism` і
  `stoic philosophy` гарантовано; промпт вимагає щонайменше п'ять широких і п'ять вузьких
  фраз, які справді вводять у пошук.
- Слова з медичним змістом (anxiety, cure, therapy, burnout...) заборонені в title, hook
  і tags: канал не обіцяє лікування (див. `STYLE_RULES`). У підсумку, де лише описується
  стан, вони дозволені.
- Модель любить дефіс U+2011 і невидимі символи: вони замінюються на звичайний `-` і
  прибираються.

Колонки в `videos`: `seo_title`, `description`, `tags` (JSON-список). `title` лишається
робочою назвою скрипта; `seo_title` — те, що піде на YouTube.

**Обкладинка** — 1280×720, JPEG, якість 90, Pillow. Рішення для читабельності:

- **Фон** обирається вимірюванням: контраст (стандартне відхилення яскравості) і яскравість
  крайової рамки (зовнішні 12%) на тому 16:9-кадрі, який справді потрапить на обкладинку
  (картинки квадратні, верх і низ відрізаються). Обидва значення нормуються 0–1 по всіх
  кандидатах і додаються з рівною вагою. Картинки з водяним знаком Pollinations і дублікати
  відкидаються.
- Фон затемнюється на 35% і отримує віньєтку.
- **Текст** — 3–5 слів великими літерами з кінця заголовка (де обіцянка), без вступного
  «10 Stoic Lessons»; якщо в заголовку є кома — береться частина після неї. Шрифт
  **Anton** (SIL OFL 1.1, з офіційного репозиторію google/fonts, у `assets/fonts/` разом із
  ліцензією), білий із чорною обводкою 4 px, по лівому краю, у нижній третині. Розмір
  підбирається перебором усіх розбиттів на 1–3 рядки: перемагає той, чий блок найближче
  до 205 px висоти (≈ третина кадру, блок починається на y=484), а серед рівних — з
  найбільшим шрифтом.
- **Перевірка читабельності.** Готова обкладинка зменшується до 210×118 і зберігається як
  `thumb_small.jpg`. Етап вимірює висоту великої літери там (поріг 10 px) і контраст білого
  тексту з картинкою під ним за формулою WCAG (поріг 4.5:1, береться 90-й перцентиль
  яскравості під літерами, тож яскрава пляма за літерою рахується проти). Невдача — це
  попередження в лог і в `events`, а не падіння відео. Є тест, який доводить, що перевірка
  вміє відповісти «ні»: білий текст на білій картинці її не проходить.
- OCR на малій версії теж запускається і логується, але нічого не вирішує. Перша версія
  перевірки саме на ньому й трималась і помилялась: на обкладинці, яку людина читає без
  зусиль, Tesseract розпізнав одне слово з трьох. Він навчений на звичайному тексті, а не
  на жирних стиснутих капітелях з обводкою.

## Один кадр на картинку, картинка завжди у своїй сцені

Схема рендеру: кожна згенерована картинка показується **один раз**, усередині
своєї сцени, на свою частку її тривалості (`double_exposure: false`). Жодних
запозичень із сусідніх сцен, повторів немає за визначенням. Кадр триває ~22
секунди — стільки ж, скільки тексту припадає на одну картинку.

**Виправлення попереднього твердження в цьому файлі.** Тут раніше було написано,
що подвійна експозиція вдвічі зменшує витрату Neurons: «82 картинки стають 41,
3936 Neurons, 39% квоти». Це була помилка в арифметиці, а не вимір. Етап
`images` рахує кількість картинок як `round(duration_s / images_per_seconds)` і
ніколи не знав, скільки разів кожну покажуть — подвійна експозиція змінювала
лише частоту зміни кадру (новий кадр кожні ~11 с замість ~22 с), а не рахунок
Cloudflare. Справжні числа, перевірені по базі відео 7: **63 картинки на 23
хвилини = 6048 Neurons = 60% добової квоти**; 30-хвилинне відео — 82 картинки =
7872 = 79%. Бюджетом керує `images_per_seconds`, і тільки він. Відмова від
подвійної експозиції тому нічого не коштує в Neurons.

**Чому відмовились.** Повтор мусив іти не одразу, інакше читався як та сама
картинка пів хвилини на екрані. Але сцена має одну-дві картинки, і всередині
сцени з однією картинкою ставити між її двома показами нічого — доводилось
позичати кадри в сусідніх сцен. Виміряно: **44% кадрів грали не у своїй сцені**.
Відповідність картинки тексту важливіша за частоту зміни кадру, тож схему
вимкнено.

**Код не викинуто**, він за прапорцем `config.render.double_exposure`. Там же
лишились `exposures_per_image`, `shuffle_*`, `movements`, `plan_shots` →
`_plan_double_exposure()`, `core.render.framing_crop()` і `contrasting_pairs()`,
і все це досі під тестами — щоб прапорець можна було повернути, а не
відновлювати схему з нуля. Що в ній уже працювало:

- **Кадрування — це реальний кроп, а не зсув zoompan.** Перша версія намагалася
  націлити zoompan на ліву/праву третину через вираз `x`. Так не могло
  працювати: при `zoom_max=1.15` вікно кропу — 87% ширини, тобто зсувається
  лише на 6.5% убік, далі ffmpeg притискає його до краю. Кожен «кадр на ліву
  третину» був звичайним центрованим наїздом. `framing_crop()` вирізає справжні
  65% ширини: виміряна різниця між лівим і правим кадром — 55.8 з 255, стільки
  ж, скільки між двома **різними** картинками (34.6).
- Повтори рознесені на 2–4 кадри, детерміновано від номера відео; дві експозиції
  завжди відрізняються і кадруванням, і напрямком зуму.

**Рух камери в поточній схемі.** 22 секунди однієї картинки не повинні здаватись
застиглими, тому рух виразніший за попередній: зум `1.08 → 1.26` плюс повільне
горизонтальне зміщення разом із зумом.

Чому не `1.0 → 1.18`: ширина діапазону та сама (0.18), але вікно кропу zoompan
має ширину `iw/zoom`, тобто простір для горизонтального зсуву — `iw - iw/zoom`.
При зумі рівно 1.0 цього простору **нуль**, зміщення не може навіть початись.
Старт із 1.08 дає 7.4% простору одразу й 20.6% у кінці. Виміряно на реальному
кадрі (середня різниця між першим і останнім кадром 19-секундного шоту,
0–255):

| схема | рух | різкість у найтіснішій точці |
|---|---|---|
| старе: зум 1.0→1.15, без зміщення | 31.3 | — |
| зум 1.0→1.18 + зміщення | 36.0 | — |
| **зум 1.08→1.26 + зміщення** | **47.5** | 23.8 проти 31.4 на найширшій |

Тобто руху на 52% більше, ніж було, і на 32% більше, ніж дало б `1.0 → 1.18`.
Ціна — 7.4% кадру обрізано завжди, і картинка на максимальному зумі м'якша
(розтягнення 2.36× від вихідних 1024 px замість 1.88×); на око на цьому стилі
непомітно, перевірено по кадру.

Напрямки чергуються за списком `config.render.pan_movements`, і порядок у ньому
підібраний так, що **горизонтальний зсув розвертається на кожному кадрі** — два
сусідні кадри ніколи не їдуть в один бік.

## Завантаження на YouTube (`pipeline/upload.py`, `publish.py`)

Покрокова інструкція зі створення `credentials.json` і першого входу: [docs/youtube-setup.md](docs/youtube-setup.md).

**Це не етап виробничого ланцюжка.** Виробництво (`run.py`) закінчується статусом `ready`;
публікація — окремий процес `python publish.py`, який бере найстаріше `ready` відео,
вантажить його й ставить `published`. Так повільний чи невдалий рендер не зсуває
публікацію (див. архітектурну вимогу нижче). Коди виходу: 0 готово або вимкнено, 1 збій,
2 помилка конфігу, 3 порожня черга. Збій повертає відео в `ready` (воно добре, збійнула
передача), а наступний запуск **продовжить** завантаження, а не почне заново.

`config.youtube_publish` має бути `true`, інакше `publish.py` нічого не вантажить: це єдиний
вимикач між «конвеєр працює» і «конвеєр постить». `config.privacy_status` (`private`,
`unlisted`, `public`) змінюється одним рядком.

- **Що відправляється:** `seo_title`, `description` і `tags` з БД, `categoryId 22`,
  `defaultLanguage en`.
- **Два обов'язкові прапори, які не винесені в конфіг:** `status.selfDeclaredMadeForKids =
  false` і `status.containsSyntheticMedia = true` (вимога YouTube до AI-контенту).
  Вони виставляються при кожному завантаженні, перевіряються на самому запиті
  перед відправкою (`assert_mandatory_flags`) і порівнюються з тим, що YouTube повернув. Якщо
  відповідь каже інше, це попередження в лозі й в `events`.
- **Резюмоване завантаження.** Всередині процесу обрив або 5xx повторюються з наростаючою
  паузою (до 10 поспіль без прогресу) і йдуть далі з байта, який має сервер. Між процесами
  адреса сесії зберігається в `output/<id>/upload_session.json` після першого чанка;
  перезапущений етап питає YouTube, скільки байтів уже є, і шле лише решту. Якщо
  завантаження вже було завершене, він забирає id відео й не шле нічого. Сесію, яку YouTube
  забув, відкидає й починає заново. Перевірено проти справжньої бібліотеки: ручне
  відновлення шле `bytes 2048-4095/4096` на збережену адресу. Відео, що вже має
  `youtube_id`, ніколи не вантажиться вдруге.
- **Обкладинка** ставиться окремим викликом `thumbnails.set`. Якщо він не вдався (найчастіше
  канал не підтверджено за телефоном), відео все одно лишається завантаженим, а причина
  пишеться як попередження.
- **Авторизація.** Один дозвіл, `youtube.upload`: за документацією `thumbnails.set` приймає
  його теж, тож ширший `youtube`, який давав би змогу керувати й видаляти все на каналі,
  не запитується. Якщо `thumbnails.set` колись відповість 403 про недостатні права, це
  один рядок у `core/youtube.py` і ще один запуск `scripts/youtube_auth.py`. Токен лежить
  у `secrets/token.json` (у `.gitignore`); для CI той самий JSON іде в GitHub Secret
  `YOUTUBE_TOKEN_JSON`. **Токен живе, лише поки екран згоди в «In production»;
  у «Testing» Google анулює його за 7 днів.**

**Про квоту: що відомо, а що ні.** Сторінка квот Google (прочитана 2 жовтня 2026,
оновлена 15 вересня 2026) каже: `videos.insert` має **власний кошик, 100 завантажень на
добу, по 1 одиниці за виклик**, `thumbnails.set` коштує ~50 одиниць із загальних 10 000.
Це збігається з тим, що ви описали щодо окремого кошика, але не з «≈100 одиниць замість
1600»: документація описує 1 одиницю в окремому кошику, а не 100 одиниць із загального.
API **не повертає** фактичну витрату, тому програма логує, які запити коштують квоту
(`output/<id>/upload.json`, поле `quota_costing_requests`), і де дивитись справжню цифру
(Cloud Console → APIs & Services → YouTube Data API v3 → Quotas & System limits). Реальну
витрату після першого завантаження треба прочитати там і записати сюди.

**Відео з неаудитованого проєкту YouTube тримає приватними** (документація `videos.insert`:
проєкти, створені після 28 липня 2020). Після завантаження повернутий `privacyStatus`
порівнюється із запитаним, і розбіжність пишеться в лог з причиною. Публікувати доведеться
вручну в YouTube Studio, доки проєкт не пройде аудит.

## Автоматизація (GitHub Actions)

Покрокове підключення секретів: [docs/github-setup.md](docs/github-setup.md).

Раннер GitHub одноразовий, а `output/` у git не йде, тому все, що має пережити між запусками,
передається явно. Репозиторій публічний: хвилини Actions безлімітні.

**Що де живе**

| що | де | чому |
|---|---|---|
| база `data/factory.db` | у git, комітиться після **кожного** запуску, у тому числі невдалого | запис про відео, сцени й журнал завершених етапів: саме з нього наступний запуск знає, з чого продовжити |
| картинки, `voice.mp3`, `timings.json`, сценарій | кеш Actions, ключ `video-<номер відео>-…` | за картинки платять Neurons, за озвучку — 19 хвилин |
| черга готових відео | **на YouTube**, `status.publishAt` на 3 дні вперед, 21:00 за Києвом | 7 файлів по 300 МБ на диску раннера не тримаються |

База закомічена без жодного секрету: перед першим комітом перевірено, що ні точні значення
ключів, ні токени не зустрічаються в таблицях, а в історії git їх немає взагалі (пошук по
кожній версії кожного файлу). Локальні тестові відео 1–6 і 8 у ній позначено як вичерпані
(`attempts = 3`), інакше перший запуск «продовжив» би відео, файлів якого в нього немає.

**Відновлення.** Запуск спершу питає базу, яке відео не завершене (`scripts/ci_state.py`),
відновлює кеш за його номером і запускає `run.py`, який пропускає етапи, записані як
завершені. Умова, яку це забезпечує і яку перевіряють тести: **повторний прогін того самого
відео не витрачає Neurons вдруге**. Відео облишається після 3 спроб або через 7 днів, щоб
один поганий сценарій не блокував канал.

**Сітка від псевдотексту в конвеєрі.** Кожна готова картинка (і вже наявна на диску) читається
в режимі PSM 11 і перемальовується з іншим сідом, доки не пройде або доки не буде трьох
спроб. Перемальовування заборонено, якщо воно залишить замало квоти на ще не створені
картинки (резерв 300 Neurons). Бюджет під справжню довжину (30 хв) — у розділі «Довжина відео» нижче: 66 картинок =
6336 Neurons, у найгіршому разі 8237. Виміряно на відео 7: строгі налаштування позначають
15 із 72 картинок, тобто очікувані ≈20% перемальовувань.

**Розклад.** `daily`: щодня 01:17 UTC, `timeout-minutes: 300`. Падіння одного запуску не зупиняє
наступного: cron спрацює завтра незалежно, і продовжить незавершене відео. `weekly`:
понеділки 06:43 UTC.

**Листи.** Простіше й безкоштовніше за SMTP: після кожного запуску workflow коментує
постійний issue «Daily run log» і згадує власника через `@`, а GitHub надсилає листа про
згадку. Жодного поштового сервера, пароля чи додаткового секрету. Ціна: лист приходить від
GitHub, а не від вас, і лише якщо в налаштуваннях сповіщень увімкнено пошту (за замовчуванням
увімкнено). Успіх: назва, посилання, коли YouTube зробить публічним. Провал: етап, текст
помилки, скільки спроб лишилось. Якщо провалилась передпольотна перевірка (`not-started`),
лист так і каже, замість того щоб видавати старе відео за результат цього запуску.

**Тижневий моніторинг** (`scripts/weekly_report.py`): скільки відео в черзі наперед
(менше 3 — попередження, менше 1 — тривога, і запуск стає червоним), скільки провалів за
тиждень, залишок квоти Cloudflare. Два чесних застереження. Черга береться з **власних
записів** системи, а не питається в YouTube: видалене в Studio відео все ще порахується.
Точного залишку квоти Cloudflare токен проєкту не бачить (потрібне право Account Analytics),
тому звіт показує Neurons, які записали власні запуски за добу (нижня межа), і живу пробу
одним реальним викликом, що каже, чи відкрита квота зараз.

**Передпольотна перевірка** (`scripts/ci_preflight.py`) іде першою й нічого не витрачає:
секрети, ffmpeg і tesseract, токен YouTube і головне: **чи може edge-tts говорити з адреси
GitHub**. Безкоштовний голос Microsoft відомий тим, що відмовляє деяким дата-центровим
адресам (403), а раннер GitHub саме така адреса. Це єдина справжня невідома автоматизації.
Якщо вона виявиться бідою, запасні шляхи: piper (офлайн, голос гірший, 236 МБ моделей треба
класти в кеш, див. `requirements-piper.txt`) або платний голос.

**Відкрите питання, яке не досліджується далі.** Коли саме Cloudflare відкриває добовий
ліміт, невідомо (див. «Відомі незавершені дрібниці»). Рішення: запуск щодня в один і той
самий час, обидві гіпотези (скидання опівночі UTC і ковзне вікно 24 години) дають однаковий
результат, поки витрата одного запуску лишається значно нижче 10 000. Очікувана витрата
≈7600 (6336 + ≈20% на перемальовування), найгірший випадок 8237, тож запас є, а межу
додатково тримає резерв 300 Neurons і заборона перемальовувань, коли бюджет підтискає. Єдине місце, де гіпотези могли б
розійтися: коли запуски сусідніх діб зсунуться на хвилини назустріч одне одному, ковзне вікно
ще містило б частину вчорашніх картинок. Це спостерігатиметься за листами; тут воно лишається
записаним як питання, а не як завдання.

## Коли щось ламається: що лікується саме, а що пишеться листом

Система працює без нагляду, тож кожен спосіб зупинитися має закінчуватися в одному з двох
місць: або він виправляється сам на наступному запуску, або лист називає одну дію. «Запуск
червоний, подивися лог» — не підходить ні туди, ні туди.

**Розклад не є обіцянкою.** Безкоштовні раннери стартують заплановане завдання тоді, коли є
вільні машини. Виміряно на цьому репозиторії: `daily` о 01:17 UTC стартував о 07:01 (+5 год
44 хв), `publish-check` о 19:11 → 22:18 (+3 год 07 хв), о 20:11 → 23:06 (+2 год 55 хв). Жоден
запуск не почався вчасно, тож затримка — норма, а не випадок; GitHub до того ж попереджає, що
за високого навантаження запуск може бути пропущений узагалі. Звідси два наслідки в коді:

- **час публікації більше не рахується від «зараз»**, а від черги: наступний слот — наступний
  день після останнього вже зайнятого (`publish_at(..., last_scheduled=...)`). Запуск о 04:17 і
  запуск о 10:01 бронюють ту саму хвилину; запуск, що переповз за північ, не перестрибує день;
  два запуски за добу не кладуть два відео на одну хвилину. Втрачений день тепер з'їдає запас,
  а не лишає дірку в ефірі;
- **два cron замість одного** (01:17 і 10:43 UTC). Другий — страхування на випадок, коли перший
  пропущено або він упав. Перед п'ятигодинним завданням працює `scripts/ci_should_run.py`: якщо
  відео на сьогодні вже готове, другий запуск нічого не робить.

**Таблиця збоїв** (`core/failures.py` — класифікація і текст дії, `scripts/notify.py` вставляє
її в лист):

| збій | лікується сам? | що буде |
|---|---|---|
| Neurons Cloudflare вичерпано | так | ліміт оновиться, наступний запуск домалює лише відсутні кадри — оплачені беруться з кешу |
| денний ліміт завантажень YouTube | так | готове відео лишається `ready`, наступний запуск вантажить його першим |
| сервіс недоступний, 5xx, таймаут | так | у межах запуску — повтор із паузою; інакше наступний запуск продовжить з етапу, що впав |
| ліміт запитів (429) | так | повтор; якщо три дні поспіль — тариф замалий для одного відео на добу |
| сценарій не пройшов власну перевірку якості | так | наступний запуск пише новий |
| обидва генератори картинок мовчать | так | кадр дублюється з попереднього, відео не зупиняється |
| токен YouTube протермінований чи відкликаний | **ні** | лист: перевипустити `scripts/youtube_auth.py` і оновити секрет `YOUTUBE_TOKEN_JSON` |
| секрет не заданий | **ні** | лист називає який саме (прольот ловить це до того, як щось витрачено) |
| edge-tts віддає 403 з адреси раннера | **ні** | лист: потрібен запасний голос, саме не минеться |
| помилка в ffmpeg | **ні** | лист: це єдиний клас, який найімовірніше є дефектом коду, а не чужим сервісом |

**Щоденна самоперевірка** (`.github/workflows/heartbeat.yml`, 19:40 UTC). Усе вище звітує про
запуск, який стався. Запуск, якого не сталося, не звітує ні про що — а саме так виглядає
пропущений cron, вимкнений за неактивністю workflow або зламаний розклад. Тому окремий
перевіряльник питає ззовні одне: чи додалося за добу нове відео в чергу? Якщо ні — лист того ж
дня, з причиною останнього збою і дією, а не тоді, коли черга скінчиться. Він також повідомляє,
коли запасу лишилося менше двох днів, коли черга порожня і коли токен перестав оновлюватися.
Коли все гаразд, він мовчить: лист, який щодня каже «усе добре», ніхто не читає.

## Послаблення на останній спробі видно, а не замовчується

План відео може бути прийнятий на третій спробі з непоправленою дрібницею — довга назва
уроку, двокрапка, перекіс у одну сферу життя — бо втрачати через це добовий ролик дорожче,
ніж випустити трохи нерівний план. Заборонене слово й скопійована назва так само лишаються
смертельними.

Послаблення, якого не видно, дорівнює правилу, якого немає. Тому кожен випадок записується
в колонку `videos.relaxed` (які саме правила обійдено, по одному запису на правило, не на
урок), згадується в листі про прогін окремим рядком і рахується в тижневому звіті: **більше
одного з останніх десяти — і звіт сам виносить це в заголовок** зі словами, що це вже не
запобіжник, а дірка, і лагодити треба не клапан, а те правило чи промпт, які між собою не
домовилися.

## Чи справді відео стало публічним (`scripts/check_published.py`)

Кожне відео вантажиться приватним із `status.publishAt`, і далі ми довіряємо YouTube зробити
його публічним у призначену хвилину. Довіряли, але не перевіряли — доти. Дві речі можуть тихо
лишити відео приватним назавжди: проєкт API без аудиту **не має права публікувати**, а
відкинуте планування виглядає точно так само, як те, що спрацювало.

**Як перевіряється, і чому саме так.** Токен завантаження має один дозвіл, `youtube.upload`,
і прочитати статус відео ним не можна: `videos.list` відповідає 403 insufficientPermissions
(перевірено). Замість того щоб розширювати права ключа, який уміє постити на канал, скрипт
питає відкритий інтернет те саме, що спитав би глядач: точка oEmbed повертає 200 і назву для
відео, яке можна подивитись, і 403 для приватного. Ні ключів, ні квоти. Перевірено на обох
випадках до написання коду: наше приватне відео дало 403, публічне стороннє — 200.

**Коли.** Workflow `publish-check` щовечора о 19:11 і 20:11 UTC, тобто по 22:11 і 21:11 за
Києвом: публікація о 21:00 за Києвом влітку це 18:00 UTC, взимку 19:00 UTC, тож два запуски
покривають обидві пори року. Пільговий період 30 хвилин.

**Лист надсилається лише коли щось не так.** Щоденний «усе гаразд» перестають читати за
тиждень, а тоді не прочитають і той один, що має значення. У листі: назва, посилання, коли
мало вийти, найімовірніша причина (аудит) і що зробити сьогодні ввечері вручну.

Три речі, які перевірка навмисно вміє:
- **Мережева помилка не є відповіддю «не опублікувалось».** Недоступна відповідь пишеться
  окремо і не рахується провалом.
- **Підтверджене відео більше не перевіряється** — подія `publish confirmed` у журналі.
- **Відео, яке ніхто не збирався публікувати** (тестове завантаження), виводиться з перевірки
  назавжди: `python scripts/check_published.py --ignore 7`. Інакше воно щовечора кричало б
  вовка, і справжню тривогу пропустили б.

Заявка на аудит YouTube API і те, що він нам дає: [docs/youtube-audit.md](docs/youtube-audit.md).

## Написи, емблеми й чергування типів кадру

**Заборонено не напис, а предмет.** Раніше заборонялися лише слова про написи («label»,
«logo»), а предмет дозволявся: мовляв, коробку можна намалювати без маркування. Вимір на
відео 7 показав, що ні. Кадр, намальований за промтом «a modest funeral invoice lying open
on a table», має **INVOICE** великими серифними літерами впоперек, і **Tesseract не читає
його за жодних налаштувань**, які я пробував (x3, контраст 2.0, PSM 6 і 11): при conf≥25
з'являється лише сміття на кшталт `Yad`, `Taal`, `Thy`. Отже підвищення чутливості цього
кадру не ловить, а ловить шум. Якщо аркуш має бути документом, на ньому буде текст. Тому
`IMAGE_BANNED_WORDS` тепер забороняє самі предмети: рахунок, чек, квиток, табло, газету,
журнал, книжку й обкладинку, пакування, номерний знак, екран з інтерфейсом, а також логотип,
емблему, герб, бейдж і торгову марку. Винятки (`IMAGE_BANNED_EXCEPTIONS`) лишають
`screen light`, `blank screen`, `face down`: світло екрана потрібне, інтерфейс ні.

**Чому сітка OCR пропустила два кадри — різні причини.**

| кадр | що насправді сталося |
|---|---|
| s2.0, «INVOICE» | **не пропущено з вини порогу**: текст стилізований і розмитий, Tesseract не бачить його ні на яких налаштуваннях. Лікується лише забороною предмета |
| s39.0, табло | **сітка його впіймала** (20 символів, певність 86) і перемалювала тричі — не допомогло, і кадр лишили |

Другий випадок і є те, що ви описали: «якщо впевнено прибрати напис не вдається, кадр має
бути без об'єктів, на яких текст узагалі буває». Тепер після трьох невдалих перемальовувань
промт переписується на сюжет, у якому письма не буває взагалі (меблі, тканина, камінь,
метал, скло, вода, рослини, їжа, погода, світло), і кадр малюється ще раз. Якщо й це не
прибрало напис, це пишеться в `events` як невирішене, а не замовчується.

**Чергування типів кадру.** Тип кожної сцени задається в коді, а не на розсуд моделі:
`SHOT_CYCLE` з дев'яти позицій — краєвид, інтер'єр, предмет, краєвид, світло, інтер'єр,
краєвид, предмет, світло. Звідси три властивості **за побудовою**: два сусідні кадри ніколи
не одного типу (у тому числі через стик циклу), краєвидів рівно **третина**, і всі чотири
типи використовуються. Модель отримує тип для кожної сцени й повертає його назад; якщо
повернутий тип не збігається із замовленим, відповідь відхиляється. Для краєвиду додатково
перевіряється наявність ознаки відкритого простору (`looks_outdoors`), інакше модель називає
«краєвидом» той самий коридор. Сцена, для якої промт так і не вийшов, отримує запасний промт
**свого типу**, а не спільний.

## Руки й обличчя: чому їх немає в кадрі

Генератор малює кисті з шістьма пальцями й трьома, і обличчя, які майже правильні й тому
гірші за явно неправильні. Полагодити це після генерації нема чим, тож єдиний спосіб —
не просити. Канал про стоїцизм, і великий план руки йому не потрібен: потрібна кімната
після розмови, перон під дощем, вікно о четвертій ранку.

**Що заборонено** (`core/prompts.py:IMAGE_ANATOMY_WORDS`, перевіряється в коді як цілі слова,
тож `handle`, `household`, `beforehand` і `surface` не спрацьовують): кисть, пальці, долоня,
кулак, зап'ясток; дієслова роботи руками — тримає, стискає, торкається, тягнеться, натискає,
гортає; обличчя, портрет, очі, вираз, усмішка; і будь-яке кадрування ближче за цілу фігуру —
`close-up`, `macro`, `head and shoulders`.

**Що дозволено:** силует проти вікна, спина, фігура на віддалі, де кисть це кілька пікселів,
і людина, якої в кадрі немає зовсім — стілець, з якого встали, пальто на гачку, увімкнене
світло. Слова `arm`, `shoulder`, `silhouette` навмисно НЕ заборонені: фігуру в контурі
генератор малює добре.

Коли саме речення сценарію про руки, кадр будується з того, що навколо:

| замість | беремо |
|---|---|
| рука тягнеться до телефона на тумбочці | телефон екраном донизу, світло на стелі, ліжко порожнє |
| пальці стискають холодний поручень | витертий латунний поручень у порожньому під'їзді, зимове світло |
| руки рахують купюри за столом | кухонний стіл уночі, купюри й монети купкою, відсунутий стілець |

**Перевірка на наявних кадрах відео 7.** Нові правила порушували **37 із 43 промтів сцен
(86%)**, за якими зроблено **60 із 70 картинок (86%)**. Найчастіші слова: `hand` 23 рази,
`fingers` 13, `palm` 7. Після перепису промтів порушень лишилось 8 із 43, і їх виправив сам
етап `images` через LLM; у підсумку 3 із 49 картинок зроблено з промта, що формально ще
зачіпає список.

**Повторне використання тепер залежить від промта.** `scene_images.prompt` зберігає промт,
яким зроблено файл. Якщо правила переписали промт, файл на диску застарів і малюється
наново. Без цього зміна правил не дійшла б до вже готових картинок. Заразом етап прибирає
файли, під які в плані немає слота: зниження `images_per_seconds` з 22 до 26 лишило 23 з 72
файлів відео 7 сиротами, і кеш Actions носив би їх вічно.

**Ціна, виміряна.** Різноманітність трохи впала: середня попарна кореляція кадрів (32×32,
відтінки сірого) зросла з +0.013 до +0.033, пар із r>0.6 стало 4 замість 1. Набір помітно
зсунувся до інтер'єрів — коридори, ліфти, стільниці, полиці — і краєвидів у ньому майже
немає, хоча їх просили. Це видно на контактному аркуші й це наступне, що варто правити.

## Довжина відео: що розійшлося у відео 7 і яка тепер перевірка

Відео 7 озвучилось у **25.0 хв** замість 28–32. Виміряно, де втрата:

| | значення |
|---|---|
| слів у сценарії відео 7 | **4098** |
| слів, які закладає config зараз (166 слів/хв, паузи 220/450/900) | **4797** |
| відео 7 від поточного бюджету | **85.4%** |
| темп, збережений у config | 166 слів/хв |
| темп, виміряний на відео 7 | 169.8 слів/хв |
| прогноз довжини при збереженому темпі | 25.6 хв (фактично 25.0) |
| прогноз при виміряному темпі | 25.2 хв |

Розійшлася **кількість слів, а не темп**: різниця темпу пояснює 0.4 хв із 5. Причина: сценарій
відео 7 написано ще за старим бюджетом 4350 слів (епоха 145 слів/хв) і з допуском ±15%; бюджет
переписали вже після нього. Перевірка на сценарії, написаному за новими правилами (відео 8):
4693 слова, 97.8% бюджету, озвучка **29.99 хв**. Структуру правити не довелось: не додано ні
уроків, ні слів, паузи не розтягувались.

Це вибірка з одного нового сценарію, тому вирішує не вона, а перевірка в коді.

**Перевірка довжини** (`run.py`, `config.length_gate`): після озвучки довжина вимірюється на
готовому треку, а не береться з прогнозу. Поза вікном **27–33 хв** сценарій відкидається,
етапи `script` і `tts` позначаються недійсними (подія `stage invalidated`, остання подія про
етап і вирішує, чи він завершений), файли озвучки видаляються, сценарій пишеться заново,
до **трьох спроб** в одному прогоні; тема лишається. Після трьох невдач відео
позначається `failed` з причиною, і за картинки нічого не заплачено, бо вони йдуть після
озвучки. Вікно ширше за 28–32, на які цілиться скрипт, бо це сітка під ціллю, а не її копія.
Відео 7 цю перевірку не проходить (25.0 < 27), відео 8 проходить.

**Картинки під справжню довжину.** За `images_per_seconds = 22` 30-хвилинне відео (відео 8, 48
сцен) вимагає **87 картинок = 8352 Neurons**, а з очікуваними ≈20% перемальовувань 10 022:
більше за ліміт. Кількість не збільшували, довшим зроблено кадр: `images_per_seconds = 26`
дає **66 картинок = 6336 Neurons**, у найгіршому разі +30% перемальовувань = 8237, під
межею 9700 (10 000 мінус резерв 300). Середній кадр ≈27 с.

## Крок 9 (CI) — рішення, прийняті наперед

- **Раннер: Linux.** Стандартний для Python/ffmpeg, швидший за Windows-раннер
  на цих задачах і без Windows Defender, який на домашній машині давав
  непередбачувані затримки під час рендеру.
- **Репозиторій ПУБЛІЧНИЙ.** Для публічних репозиторіїв хвилини GitHub Actions
  безлімітні. На приватному 30 відео на місяць не влізуть у 2000 безкоштовних
  хвилин: рендер одного 23-хвилинного відео на слабкому CPU займає ~50 хвилин,
  на 2-ядерному раннері очікувано 60–90 хвилин, тобто 30 відео — це 1800–2700
  хвилин лише на рендер, без решти етапів.
- **Наслідок для секретів:** усі ключі йдуть у GitHub Secrets, ніколи в код.
  `.gitignore` відповідно посилено (`.env*` з винятком для `.env.example`,
  `*.db`, `*.key`, `*.pem`, `output/`, `logs/`, `data/`). Історію git
  перевірено: жоден секрет, БД чи файл з `output/` ніколи не комітився.

## Відомі незавершені дрібниці

- **Коли Cloudflare відкриває добовий ліміт — досі не з'ясовано.** Журнал проб:
  `logs/cloudflare_window.jsonl`, один виклик пише один рядок
  (`python scripts/cf_window_probe.py`; невдала проба не коштує Neurons).

  | час (UTC) | результат |
  |---|---|
  | 2 жовтня 06:46 | HTTP 429, код 4006, «you have used up your daily free allocation» |
  | 2 жовтня 20:50 | HTTP 200, 96 Neurons |
  | 3 жовтня 07:29 | HTTP 200, 96 Neurons |

  Документоване скидання о 00:00 UTC не підтверджується: о 06:46 UTC 2 жовтня, майже через
  7 годин після опівночі, ліміт був ще закритий, а на панелі Cloudflare лічильник показував
  0/10k. Отже текст помилки про «вичерпану добову квоту» розходиться з тим, що показує
  панель. Відкрився він десь між 06:46 і 20:50 UTC.

  **Проба 3 жовтня нічого не доводить.** Вона успішна, але узгоджується з обома гіпотезами
  (скидання опівночі UTC і ковзне вікно 24 години), бо за добу до неї витрачено 7776 з
  10 000 — менше за ліміт у будь-якому разі. Щоб розрізнити їх, потрібна проба наступного
  ранку **після** дня, коли витрачено близько 10 000.

  Витрата за 2 жовтня UTC: **7776 Neurons** — 6720 на 70 картинок відео 7, 864 на дев'ять
  картинок порівняння стилю, 192 на дві поодинокі проби. Виклики, що впали з 4006, не
  коштують нічого.

- **Моделі Cloudflare з width/height не перевірені.** Чи приймають ширину й висоту
  `stable-diffusion-xl-base-1.0`, `stable-diffusion-xl-lightning` і `dreamshaper-8-lcm`,
  досі невідомо; скрипт готовий: `python scripts/cf_model_probe.py`. Доки ні — лишається
  квадрат від `flux-1-schnell` із кропом до 16:9.
- **Перезапуск етапів на тому самому відео лишає застарілі кліпи.** Рендер пропускає сцену,
  якщо `clips/scene_NNN.mp4` уже існує, а кеш попереднього масштабування названий за
  іменем файлу картинки. Після нової озвучки (інші тривалості сцен) чи нових картинок
  старі кліпи й кеш треба видаляти вручну: `output/<id>/clips/`. Для нових відео, які
  завжди йдуть у новий каталог, це не проявляється.
- Стиль зображень (`image_style`) містить «no text, no lettering, no watermark, no modern
  branding». FLUX на `steps=2` негативні вказівки майже ігнорує, і згадка про «text» може
  навіть підштовхувати модель його малювати; без вимірювання це лише гіпотеза, тож
  стиль не чіпали. Перевірка заборонених слів його не сканує (`_split_style`).

- Відео 7, сцени 12 і 13 (зображення `scene_012_00.jpg` і `scene_013_00.jpg`):
  згенеровані через Pollinations-відкат після вичерпання добового ліміту
  Cloudflare 1 жовтня 2026, тому мають водяний знак `pollinations.ai` в кутку.
  Перегенерувати через Cloudflare разом із наступною роботою, коли ліміт
  скинеться — окремого прогону заради цього не робити.

## Архітектурна вимога до кроків 8 і 9: виробництво окремо від публікації

Головне правило системи: **публікація на YouTube відбувається точно за графіком,
незалежно від того, скільки тривав рендер і чи він узагалі вдався.** Тому це два
незалежні процеси, а не етапи одного ланцюжка.

**Виробництво** — працює вночі, коли завгодно й скільки завгодно. Робить відео і
кладе в чергу зі статусом `ready`. Якщо зависло, зламалось чи не встигло — нічого
страшного, бо ніхто на нього не чекає. Ціль: тримати в черзі запас на 5–7 днів.

**Публікація** — окремий процес, стартує о заданій годині, бере найстаріше відео
зі статусом `ready`, вантажить на YouTube, ставить `published`. Триває хвилини,
бо нічого не рендерить. Якщо черга порожня — шле попередження і не публікує
нічого (краще пропуск дня, ніж випадкове відео).

**Жорсткі таймаути на кожному рівні, усі в config:** на підкадр (вже є,
`render.subshot_timeout_s`), на сцену, на весь рендер, на весь прогін
виробництва. Перевищення — відео позначається `failed`, процес іде далі до
наступного. Жоден етап не має права висіти вічно. Підстава з практики: на
відео 7 дві сцени зависли на 76 і 41 хвилину без жодної причини, яку вдалося
знайти, — разом 117 хвилин проти 31 хвилини корисної роботи.

**Переходи між сценами — fade, не xfade.** `xfade` на 43 кліпи виміряно: не
завершився за 1 годину 50 хвилин і був обірваний. `concat` тих самих кліпів із
`-c copy` — **3.9 секунди**. Тому: `fade in` 0.5с на початку і `fade out` 0.5с у
кінці кожного кліпу просто під час рендеру сцени, далі concat demuxer. Для
спокійного оповідного відео виглядає практично так само, а склейка стає миттєвою.

**Моніторинг черги:** щодня рахувати відео зі статусом `ready`. Менше трьох —
попередження, менше одного — тривога.
