# YouTube Content Factory

Система, яка щодня автоматично робить відео для YouTube-каналу про стоїцизм і
практичну філософію (англійською, 25–35 хв) і публікує їх.

**Поточний стан:** реалізовано `topic`, `script`, `tts` і `images`. Решта етапів — заглушки.

## Налаштування

```
cp .env.example .env
```

Далі впиши в `.env` ключ `GROQ_API_KEY` (https://console.groq.com/keys).
`GEMINI_API_KEY` необовʼязковий: якщо він є, Gemini працює як резерв, якщо ні —
резерв просто пропускається. Файл `.env` у `.gitignore`, комітити його не можна.

Для озвучення (`tts`) потрібен один із двох провайдерів:

- **piper** (за замовчуванням, офлайн): `pip install piper-tts`, потім завантаж
  голоси (~236 МБ, у `.gitignore`, не комітяться):
  ```
  python -m piper.download_voices --download-dir assets/voices en_US-ryan-high en_GB-alan-medium en_US-joe-medium
  ```
- **edge-tts** (хмара Microsoft, безкоштовно, без ключа): `pip install edge-tts`.
  З деяких серверних IP повертає 403 — це видно в лозі як зрозуміле пояснення,
  не стектрейс, і означає "спробуй piper на цій машині".

Обирається полем `tts.provider` у `config.json` (`"piper"` або `"edge"`).
`ffmpeg` має бути в PATH — використовується для конвертації mp3→wav (edge) і для
склеювання сцен в один `narration.wav`.

Для ілюстрацій (`images`) потрібен Cloudflare Workers AI:

- Безкоштовний акаунт на dash.cloudflare.com, картка не потрібна.
- `CLOUDFLARE_ACCOUNT_ID` — зі сторінки Workers AI, панель «Use REST API».
- `CLOUDFLARE_API_TOKEN` — My Profile → API Tokens → Create Custom Token з правами
  `Account` / `Workers AI` / `Read` **і** `Account` / `Workers AI` / `Edit` (обидва
  одночасно), Account Resources звужено до одного акаунта.
- Резерв — `POLLINATIONS_TOKEN`, той самий, що й вище.

Безкоштовний ліміт — 10 000 Neurons/добу, поновлюється щодня.

OCR-перевірка (опційна, можна пропустити — усе працює й без неї):

```
winget install --id UB-Mannheim.TesseractOCR -e
pip install pytesseract Pillow
```

Якщо `tesseract.exe` не знайдено, перевірка просто вимикається, без помилки.

## Запуск

```
python run.py            # створює запис у БД і проходить усі етапи
python run.py --dry-run  # лише показує етапи, БД не чіпає
python tests/test_failure_path.py
```

Потрібен Python 3.11+. Зовнішніх залежностей немає, лише стандартна бібліотека.

## Структура

- `config.json` — налаштування каналу, відео, `image_style`, блок `tts`
- `run.py` — оркестратор (помилка етапу → статус `failed`, процес не падає)
- `core/` — config, db (SQLite), logger, retry, validate, llm, prompts, text, tts
- `pipeline/` — етапи: topic, script, tts, images, render, thumbnail, seo, upload
- `scripts/preview.py` — показує заголовок, засів, уроки й перші речення кожної
  частини одного відео, без читання 5000 слів
- `scripts/tts_sample.py` — рендерить один уривок усіма голосами-кандидатами,
  щоб вибрати голос на слух
- `scripts/contact_sheet.py` — складає всі зображення відео в одну сітку
  (`output/<video_id>/contact_sheet.jpg`), щоб оцінити узгодженість набору
  одним поглядом, не відкриваючи по одній
- `assets/topic_seeds.json` — 48 стоїчних тем-засівів
- `assets/voices/` — моделі Piper (у `.gitignore`, качаються окремо)
- `data/factory.db` — база (у `.gitignore`)
- `output/<video_id>/` — `concept.json`, `outline.json`, `script.txt`,
  `narration.wav`, `audio/scene_NNN.wav`
- `logs/factory.log` — лог (у `.gitignore`)

## Як працює генерація

**`core/llm.py`** — Groq (`llama-3.3-70b-versatile`) основний, Gemini резервний.
Не більше 25 запитів на хвилину, окрема обробка 429 з очікуванням замість падіння,
`complete_json()` вміє витягати JSON із ```json-блоків і перепитує, якщо парсинг
не вдався. Кожен виклик логується: модель, токени, час.

**`pipeline/topic.py`** — бере засів, який найрідше використовувався (рахується
по колонці `videos.seed`), просить у моделі концепцію, перевіряє на дублі через
`topic_exists()` і схожість ≥0.75 з останніми 200 темами. До 5 спроб із різними
засівами.

**`pipeline/script.py`** — чотири стадії, не один запит:

| Стадія | Що робить | Запитів |
|---|---|---|
| A | план: заголовок, обіцянка, 10 назв уроків | 1 |
| B | кожен урок окремо (~395 слів), з передачею вже написаного | 10 |
| C | гачок (~200 слів) і фінал (~200 слів) | 2 |
| D | розбивка на сцени **програмно** + image_prompt пакетами по 10 | ~5 |

Бюджет слів: `target_duration_min × words_per_minute` = 4350.

Перед записом у БД перевіряється: сума слів у межах ±15% бюджету, 40–60 сцен,
у жодній сцені немає markdown і порожнього тексту, у кожної сцени є image_prompt.
Якщо слів не вистачає або забагато — перегенеровуються лише найгірші уроки
(до 3 раундів), а не весь сценарій. Кількість сцен коригується програмно зміною
цільового розміру сцени.

Кожен урок прив'язаний до теми засіву явно (назва + `angle_hints`), і план
відкидається, якщо більше 4 з 10 уроків потрапляють в один домен (телефон,
робота, сім'я...) — щоб 30 відео не зійшлися в узагальнену самодопомогу. Власні
імена й рідкісні кольори, якими зловживала модель у минулих відео, записуються
в таблицю `tics` і забороняються в наступних промтах; ім'я, повторене в одному
відео більше 3 разів, замінюється програмно.

**`pipeline/tts.py`** — кожна сцена озвучується окремо
(`output/<video_id>/audio/scene_NNN.wav`), потім склеюються в `narration.wav`.
Реальний темп (слів/хв) вимірюється з готового аудіо і звіряється з
`config.words_per_minute`; відхилення понад 15% пишеться в лог і в `events`
як попередження, не як помилка — саме відео при цьому не відкидається.

**`pipeline/images.py`** — кожна сцена отримує кілька зображень:
`max(1, round(duration_s / images_per_seconds))`, усі на одному `image_prompt`,
кожне зі своїм seed. Порядок відкату на зображення: Cloudflare Workers AI
(`flux-1-schnell`) → pollinations.ai → повторне використання останньої вдалої
картинки (без копіювання файлу, просто той самий шлях ще раз) — справжньою
відсутньою залишається лише перша картинка відео, якщо вона не вийшла, бо
дублювати ще нічого. Перші 5 успішних генерацій Cloudflare логують реальний
Neurons (виміряно: **96 на картинку при `steps=2`**, не орієнтовні ~19–20 з
документації провайдера), і стадія рахує прогноз на все відео проти ліміту
10 000/добу з явним попередженням, якщо не влазить.

Перед генерацією кожен `image_prompt` проганяється через список заборонених
іменників (`core/prompts.py:IMAGE_BANNED_WORDS` — телефони, екрани, коробки,
етикетки, книжки, логотипи) і переписується моделлю, якщо знайдено збіг;
виправлення пишеться назад у `scenes.image_prompt`. Це головний захист:
FLUX на `steps=2` майже ігнорує негативні інструкції в стилі («no text»),
тож єдиний надійний спосіб — не згадувати об'єкт, який тягне за собою текст,
узагалі. Опційний другий шар — OCR через Tesseract по готовій картинці;
**перевірено на реальному прикладі з текстом — не спрацював** (ШІ малює
псевдотекст, що не формує справжніх гліфів, а Tesseract натренований на
реальних шрифтах), тож це радше остання сітка безпеки, ніж основний захист.

## Чому подвійна експозиція обов'язкова (реалізовано в `pipeline/render.py`)

Добовий безкоштовний ліміт Cloudflare — 10 000 Neurons, і це не з запасом.
30-хвилинне відео при поточних налаштуваннях (`images_per_seconds=22`,
`steps=2`, 96 Neurons/картинку) — це ~82 картинки = **7872 Neurons, 79% добової
квоти на одне відео й практично нуль запасу на помилки та OCR-регенерації**.
Для каналу, що публікує щодня, це непрацездатно: один невдалий день (більше
ретраїв через нестабільність Cloudflare/Pollinations) і бюджету не вистачить.
Перевірено на практиці 1 жовтня 2026: саме так і сталося під час тестування.

Тому кожне згенероване зображення показується в кадрі двічі замість генерації
другого зображення. Глядач бачить два різні кадри, Cloudflare платиться за
один. 82 картинки на відео стають 41: витрата падає до 3936 Neurons (39%
квоти), запас зростає до 61%. Це не покращення на розсуд, а умова, без якої
щоденний випуск відео не вкладається в безкоштовний рівень.

Щоб повтор справді читався як інший кадр, а не як та сама картинка:

- **Кадрування — це реальний кроп, а не зсув zoompan.** Перша версія намагалася
  націлити zoompan на ліву/праву третину через вираз `x`. Так не могло
  працювати: при `zoom_max=1.15` вікно кропу — 87% ширини, тобто може зсунутись
  лише на 6.5% убік, далі ffmpeg його притискає до краю. Кожен «кадр на ліву
  третину» на практиці був звичайним центрованим наїздом, через що обидві
  експозиції виглядали однаково. Тепер `core.render.framing_crop()` вирізає з
  картинки справжні 65% ширини (ліві або праві) і розтягує їх на весь екран.
  Виміряно на одному зображенні: середня різниця між лівим і правим кадром —
  **55.8 з 255** (до виправлення кадри були практично ідентичні).
- **Дві експозиції завжди відрізняються і кадруванням, і напрямком зуму.**
  Пари беруться з `config.render.movements` через `core.render.contrasting_pairs()`.
- **Повтори рознесені в часі.** Другий показ іде не одразу, а через 2–4 інші
  кадри (порядок A B C A D B). План будується детерміновано від номера відео,
  тож перезапуск продовжує те саме відео, а не починає нове.

Ціна рознесення, прямо: сцена отримує одну картинку на 22 секунди тексту, тобто
здебільшого одну або дві. Усередині сцени з однією картинкою ставити між її
двома показами нічого — тому план будується блоками по 3+ картинки з сусідніх
сцен, і картинка може зіграти на одну сцену раніше або пізніше за свій текст.
Виміряно на відео 7 (43 сцени, 63 картинки, 126 кадрів): жодного повтору
підряд, 97% повторів у заданому проміжку 2–4 кадри, 56% кадрів лишаються у
власній сцені, решта — рівно на одну сцену вбік, далі не йде ніхто. Тривалості
слотів беруться зі сцени, якій слот належить, тож перемішування не може зсунути
межу сцени й розсинхронізувати звук.

## Крок 9 (CI) — рішення, прийняті наперед

- **Раннер: Linux.** Стандартний для Python/ffmpeg, швидший за Windows-раннер
  на цих задачах і без Windows Defender, який на домашній машині давав
  непередбачувані затримки під час рендеру.
- **Репозиторій ПУБЛІЧНИЙ.** Для публічних репозиторіїв хвилини GitHub Actions
  безлімітні. На приватному 30 відео на місяць не влізуть у 2000 безкоштовних
  хвилин: рендер одного 23-хвилинного відео на слабкому CPU займає ~50 хвилин,
  на 2-ядерному раннері очікувано 60–90 хвилин, тобто 30 відео — це 1800–2700
  хвилин лише на рендер, без решти етапів.
- **Наслідок для секретів:** усі ключі йдуть у GitHub Secrets, ніколи в код.
  `.gitignore` відповідно посилено (`.env*` з винятком для `.env.example`,
  `*.db`, `*.key`, `*.pem`, `output/`, `logs/`, `data/`). Історію git
  перевірено: жоден секрет, БД чи файл з `output/` ніколи не комітився.

## Архітектурна вимога до кроків 8 і 9: виробництво окремо від публікації

Головне правило системи: **публікація на YouTube відбувається точно за графіком,
незалежно від того, скільки тривав рендер і чи він узагалі вдався.** Тому це два
незалежні процеси, а не етапи одного ланцюжка.

**Виробництво** — працює вночі, коли завгодно й скільки завгодно. Робить відео і
кладе в чергу зі статусом `ready`. Якщо зависло, зламалось чи не встигло — нічого
страшного, бо ніхто на нього не чекає. Ціль: тримати в черзі запас на 5–7 днів.

**Публікація** — окремий процес, стартує о заданій годині, бере найстаріше відео
зі статусом `ready`, вантажить на YouTube, ставить `published`. Триває хвилини,
бо нічого не рендерить. Якщо черга порожня — шле попередження і не публікує
нічого (краще пропуск дня, ніж випадкове відео).

**Жорсткі таймаути на кожному рівні, усі в config:** на підкадр (вже є,
`render.subshot_timeout_s`), на сцену, на весь рендер, на весь прогін
виробництва. Перевищення — відео позначається `failed`, процес іде далі до
наступного. Жоден етап не має права висіти вічно. Підстава з практики: на
відео 7 дві сцени зависли на 76 і 41 хвилину без жодної причини, яку вдалося
знайти, — разом 117 хвилин проти 31 хвилини корисної роботи.

**Переходи між сценами — fade, не xfade.** `xfade` на 43 кліпи виміряно: не
завершився за 1 годину 50 хвилин і був обірваний. `concat` тих самих кліпів із
`-c copy` — **3.9 секунди**. Тому: `fade in` 0.5с на початку і `fade out` 0.5с у
кінці кожного кліпу просто під час рендеру сцени, далі concat demuxer. Для
спокійного оповідного відео виглядає практично так само, а склейка стає миттєвою.

**Моніторинг черги:** щодня рахувати відео зі статусом `ready`. Менше трьох —
попередження, менше одного — тривога.
